## What this is

PDF Scanner: a Windows desktop app (Go + Wails v2 + Vue 3) that fuzzy-searches a folder of
PDFs and displays hits in an embedded PDF.js viewer or an external reader.

The project was reworked from Electron + Python to Go + Wails in commit `a6ea5a7`. There is
no Python and no Electron left — a leftover WinPython folder or `dist-electron/` from an
older checkout is dead weight and can be deleted.

## Layout

```
build.ps1            Build entry point: toolchain check, Go checks, CGO workaround, wails build
main.go              Wails bootstrap; embeds frontend/dist, binds *App, file-drop wiring
app.go               Bound API surface (the methods the frontend can call)
internal/match/      Keyword scoring — pure strings, no PDF dependency, unit-tested
internal/search/     PDF walking + text extraction (MuPDF via go-fitz)
internal/ocr/        Rasterise + Tesseract subprocess for scans (imports go-fitz)
internal/ocr/textcache/  Recognised text on disk, keyed by file hash — no PDF dependency
internal/opener/     Launches Acrobat at a given page, or the system default handler
frontend/            Vue 3 + Vite SPA (JS with `script setup`, TS only for entry/config)
frontend/wailsjs/    GENERATED by the Wails CLI — not committed
build/               Wails packaging assets (icon, manifest, version info)
```

### Naming

One name, two spellings: `pdf_scanner` is the identifier (repo, Go module, npm package,
`wails.json` → `name`, `%AppData%\pdf_scanner\`), **PDF Scanner** is the only spelling the
user ever sees (window title, `<title>`, header, `productName`, `PDF Scanner.exe`). Settings
written by the old `pdf-searcher` directory are migrated once on startup by
`migrateLegacySettings()` in [app.go](app.go).

Frontend ⇄ backend goes through Wails bindings plus three events: `search-progress`
(`progress`, `completed`, `total` — the UI shows the file counter, the percentage drives the
bar), `ocr-progress` (the same plus `fileIndex`/`fileTotal`/`fileName`/`page`/`pageTotal`,
because recognition is counted in pages across several files) and `files-dropped` for native
drag & drop.

### Bound Go API (`app.go`)

| Method | Signature | Purpose |
| --- | --- | --- |
| `LoadSettings` | `() Settings` | Read `settings.json`, fill defaults |
| `SaveSettings` | `(Settings) error` | Non-destructive merge back to disk |
| `GetPDFsFolder` | `() string` | The folder that gets searched |
| `SelectPDFsFolder` | `() (string, error)` | Native folder picker; persists the choice |
| `SearchPDFs` | `(folder, keyword string) (search.Outcome, error)` | Runs the search |
| `CancelSearch` | `()` | Aborts the run in flight |
| `OpenPDF` | `(path string, page int) error` | Opens the file in an external reader at `page` |
| `LoadPDF` | `(path string) ([]byte, error)` | Raw bytes for the in-app PDF.js viewer |
| `SelectFiles` | `() ([]string, error)` | Native multi-select dialog, `*.pdf` filter |
| `CopyFileToPDFsFolder` | `(src string) (string, error)` | Copies `src` in; returns the stored name |
| `OCRStatus` | `() ocr.Info` | Is Tesseract present, and which languages does it have |

| `CancelOCR` | `()` | Aborts the recognition run in flight |

Every method that can fail returns an `error`. Wails maps a non-nil Go error to a rejected
promise, which the frontend turns into a toast and an inline message
(`frontend/src/composables/useError.js`).

### Settings

`%AppData%\pdf_scanner\settings.json` (`os.UserConfigDir()`):

```json
{
  "theme": "light",
  "language": "de",
  "searchHistory": [{ "timestamp": "21.8. 22:28", "keyword": "..." }],
  "highlightColor": "#9B59B6",
  "pdfsFolder": "C:\Users\<you>\Documents\PDFs"
}
```

Recognised text lives beside it in `%AppData%\pdf_scanner\ocr-cache\`, one JSON file per
document named for its SHA-256. Nothing about OCR is stored in `settings.json`: the language
is asked for per run, not remembered.

`pdfsFolder` is editable from the sidebar and created on startup if missing. `theme` and
`language` are persisted but **not read by the UI** — the theme actually lives in
`localStorage`, and every string is hardcoded German.

## How the search works

Backend (`internal/search`, `internal/match`):

1. `filepath.Walk` collects every `*.pdf` under the configured folder, recursively. A
   missing folder is an error, not an empty result.
2. A worker pool bounded to `runtime.NumCPU()` — each worker holds an open MuPDF document
   through cgo.
3. Per page: `doc.Text(page)` only. No HTML serialisation.
4. Each line is scored by `match.Score`, a five-strategy cascade: case-insensitive
   substring (100), normalised scientific name (95), token equality after normalisation
   (90), Levenshtein ratio via go-edlib (computed), character 3-gram Jaccard similarity
   over short token spans (computed).

   Both computed strategies are **directional**, and that direction is the whole game.
   Strategy 4 slides the *keyword* along a token that is longer than it; sliding a shorter
   token along the keyword asks the reverse question and answers it with 100 for any token
   that is merely a fragment of the keyword.
   A token shorter than the keyword is
   scored by the plain ratio, which charges it for the length it is missing. Strategy 5
   scores *spans* rather than the whole line, because MuPDF extracts some pages as one
   paragraph-long "line", whose n-gram set dilutes any keyword to nothing; spans are sliced
   out of the line by byte offset so the returned word stays a genuine substring of it,
   which the viewer relies on to place the highlight.
5. Lines below `match.MinConfidence` (85) are dropped. That number is now measured rather
   than inherited: `TestThresholdSweep` runs a fixture set of real corpus lines with human
   verdicts at every threshold from 50 to 100 and reports the band that classifies them all
   correctly. It is `[82, 85]`, and 85 is deliberately its top edge — above it the errors
   are missed hits, below it they are near-miss.
   Survivors collapse per
   `(page, foundWord)` into one `SearchResult` whose `Occurrences` counts every hit those
   lines contained, so a term found eight times on one page is eight, not one. Results are
   sorted by confidence descending, then file, page and word — the tie-break exists because
   without it the order came from whichever worker finished first, and the same search
   listed the same files differently twice in a row.
6. Files MuPDF cannot open land in `Outcome.Failures`; files it opens but gets no text out
   of are looked up in the OCR cache, and land in `Outcome.Textless` only if nothing has
   been recognised for them yet. Both are reported in the UI, and the split matters — a
   scanned PDF returns nothing for *every* keyword, so without it "not in this file" and
   "this file cannot be searched at all" look identical to the user. A scan that *has*
   been recognised is searched like any other file; its hits carry `Match: "ocr"` and
   `Outcome.OCRFiles` counts them.
7. The run honours its `context.Context`: a new search cancels the previous one, and the
   cancel button cancels the current one.

Highlights (`frontend/src/composables/usePdfViewer.js`): the backend returns **no**
rectangles. go-fitz exposes no structured text API (only `Text`, `HTML`, `SVG`, `Image`,
`Links`, `ToC`, `Metadata`, `Bound`), so geometry is derived in the frontend: the viewer
locates the term in PDF.js' text layer and composes each text item's own `transform` with
`viewport.transform`. That accounts for glyph metrics, page rotation and a non-zero CropBox
origin. Consequence: a scanned page with no text layer gets no highlight, and the viewer
says so rather than drawing a box in the wrong place.

## How OCR works

Scans have no text layer, so extraction returns nothing for every keyword. `internal/ocr`
gives them one, and `internal/ocr/textcache` makes that a one-time cost.

**When it runs.** Never during a search. Recognition is seconds per page — the 31-page test pdf is minutes — so a search that stopped to OCR
would hang on the first run after a scan is added, with nothing on screen. Instead the
search returns, reports its textless files, and
[OcrPanel.vue](frontend/src/components/OcrPanel.vue) offers to recognise them. The results
the user is already reading stay up while it works, and when it finishes `SearchComponent`
re-runs the same keyword — this time the cache answers, and the scan has hits.

**The language is asked for every time.** Tesseract cannot tell German from English by
itself: `--psm 0` detects *script* and orientation, and both are Latin. There is no language
identification in the engine, so something must say which model to load, and a remembered
answer is silently wrong for the next document. The picker lists the installed languages and
adds a combined `deu+eng` when both are present, because Tesseract takes several at once and
lets them compete per word — which is what a German document quoting an English abstract
needs. The choice is cleared whenever the textless file list changes, which is what makes
the question get asked again; it is deliberately *not* in `settings.json`.

**The cache is keyed on content, not path.** `textcache` stores one JSON file per document,
named for the SHA-256 of its bytes. Renaming, moving or re-importing a file reuses its text;
editing it misses and re-runs. The language is recorded *in* the entry rather than folded
into the key — two entries for one document would leave the search with no way to choose
between them, so re-running in another language replaces the entry. Only textless files are
hashed, so the cost falls on the handful of scans rather than on every file in the folder on
every search. Writes go through a temp file and a rename, and a cancelled run caches nothing:
a half-recognised document would otherwise read back as a whole one forever.

**Tesseract is a subprocess, not a library.** gosseract would link libtesseract through cgo,
adding a second native dependency to a build that already needs a linker workaround for
MuPDF. One process per page is a rounding error next to the recognition itself.
`ocr.Locate()` prefers a copy bundled at `<exe dir>/tesseract/`, then `PATH`, then the usual
installer paths; `ocr.Status()` reports a missing engine as a state the UI renders, never as
an error. Pages are rasterised with `doc.ImagePNG(page, 300)` and piped in on stdin, so no
temporary files are involved. Each process runs with `OMP_THREAD_LIMIT=1` and the pool is
one process per core — letting every process fan out again oversubscribes the machine badly
enough to be slower than running them one at a time.

**Consequences worth knowing.** An OCR hit cannot be highlighted: the viewer derives geometry
from PDF.js' text layer, and a scan has none. Those hits are marked `OCR` in the result list
and say so in the tooltip. And OCR errors feed the same scorer at the same 85-point
threshold, which was tuned so near-miss drug names fall *below* it — so a wrong-language
model does not just misread, it pushes genuine hits under the gate.

## Building

[build.ps1](build.ps1) is the entry point: it checks the toolchain (go / node / npm / wails
/ gcc, and Wails CLI >= 2.15), runs the Go checks, exports the `CGO_LDFLAGS` workaround
below, and calls `wails build -clean`. `-Dev` runs `wails dev` instead, `-SkipChecks` skips
the checks, `-NoClean` keeps `build/bin`, `-Platform` overrides `windows/amd64`. It probes
the usual MSYS2 locations for `gcc` and prepends the one it finds to `PATH` for the build,
so MSYS2 does not have to be on the system `PATH`.

Note it is ASCII-only on purpose: Windows PowerShell 5.1 reads a BOM-less file as CP1252,
which turns a UTF-8 em dash into a smart quote and breaks parsing.

Underneath, `wails dev` / `wails build` are the only working entry points on a clean
checkout:

- `go build ./...` → `pattern all:frontend/dist: no matching files found`
- `npm run build` → `Could not resolve "../wailsjs/go/main/App"` (bindings are generated,
  not committed)

Go-only checks that *do* work without the frontend:

```sh
go build ./internal/...
go vet ./internal/...
go test ./internal/match/ ./internal/ocr/textcache/   # no cgo, no C toolchain needed
```

Those two test packages are listed one by one rather than as `./internal/...` on purpose:
`internal/search` and `internal/ocr` import go-fitz, which loads MuPDF at init — through cgo,
or through `libmupdf.dll` on the `nocgo` path — so their test binaries need the toolchain
either way. Keeping the scorer and the cache free of that import is what keeps them testable
on a bare checkout.

Toolchain notes:

- Wails CLI v2.12 cannot generate bindings under Go 1.27 (`internal error: package "os"
  without types was imported`). Use v2.15+.
- go-fitz ships a prebuilt MuPDF static library referencing `__intrinsic_setjmpex`, which
  mingw-w64 v12+ no longer provides. It is MSVC's name for the CRT's `_setjmpex`, which
  mingw does ship in `libmsvcrt.a`, so alias it:
  `CGO_LDFLAGS="-Wl,--defsym=__intrinsic_setjmpex=_setjmpex" wails build`.
  Verified with mingw-w64 GCC 14.1.0 (MSYS2 MINGW64) and go-fitz v1.28.2.

The version in the UI and on the `.exe` both come from `wails.json` → `info.productVersion`;
Vite reads it at build time.
