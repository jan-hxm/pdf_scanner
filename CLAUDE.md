# CLAUDE.md

Working context for this repository. User-facing information lives in [README.md](README.md);
open work items in [To-Do.md](To-Do.md).

## What this is

PDF Scanner: a Windows desktop app (Go + Wails v2 + Vue 3) that fuzzy-searches a folder of
PDFs and displays hits in an embedded PDF.js viewer or an external reader.

The project was reworked from Electron + Python to Go + Wails in commit `a6ea5a7`. There is
no Python and no Electron left — a leftover WinPython folder or `dist-electron/` from an
older checkout is dead weight and can be deleted.

## Layout

```
build.ps1            Build entry point: toolchain check, Go checks, CGO workaround, wails build
Get-Tesseract.ps1    Stages Tesseract + language data into build/tesseract for bundling
main.go              Wails bootstrap; embeds frontend/dist, binds *App, file-drop wiring
app.go               Bound API surface (the methods the frontend can call)
internal/match/      Keyword scoring — pure strings, no PDF dependency, unit-tested
internal/search/     PDF walking + text extraction (MuPDF via go-fitz)
internal/ocr/        Rasterise + Tesseract subprocess for scans (imports go-fitz)
internal/ocr/textcache/  Recognised text on disk, keyed by file hash — no PDF dependency
internal/opener/     Launches Acrobat at a given page, or the system default handler
frontend/            Vue 3 + Vite SPA (JS with `script setup`, TS only for entry/config)
frontend/wailsjs/    GENERATED by the Wails CLI — not committed
packaging/           Wails packaging assets (icon, manifest, version info) — the sources
build/               GENERATED and untracked: the binary, the Tesseract bundle, the cache
```

### Naming

One name, two spellings: `pdf_scanner` is the identifier (repo, Go module, npm package,
`wails.json` → `name`, `%AppData%\pdf_scanner\`), **PDF Scanner** is the only spelling the
user ever sees (window title, `<title>`, header, `productName`, `PDF Scanner.exe`). Settings
written by the old `pdf-searcher` directory are migrated once on startup by
`migrateLegacySettings()` in [app.go](app.go).

Frontend ⇄ backend goes through Wails bindings plus three events: `search-progress`
(`progress`, `completed`, `total` — the UI shows the file counter, the percentage drives the
bar), `ocr-progress` (the same plus `fileIndex`/`fileTotal`/`fileName`/`page`/`pageTotal`,
because recognition is counted in pages across several files) and `files-dropped` for native
drag & drop.

promise, which the frontend turns into a toast and an inline message

### Settings

`%AppData%\pdf_scanner\settings.json` (`os.UserConfigDir()`):

```json
{
  "theme": "light",
  "language": "de",
  "searchHistory": [{ "timestamp": "21.8. 22:28", "keyword": "..." }],
  "highlightColor": "#9B59B6",
  "pdfsFolder": "C:\Users\<you>\Documents\PDFs"
}
```

Recognised text lives beside it in `%AppData%\pdf_scanner\ocr-cache\`, one JSON file per
document named for its SHA-256, carrying the pages plus the `fileName`, `languages`, `dpi`
and `engine` it was produced with — which is where to look when a scan searches oddly. The
sidebar reports its size and clears it. Nothing about OCR is stored in `settings.json`: the
language is asked for per run, not remembered.

`pdfsFolder` is editable from the sidebar and created on startup if missing. `theme` and
`language` are persisted but **not read by the UI** — the theme actually lives in
`localStorage`, and every string is hardcoded German.

## How the search works

Backend (`internal/search`, `internal/match`):

1. `filepath.Walk` collects every `*.pdf` under the configured folder, recursively. A
   missing folder is an error, not an empty result.
2. A worker pool bounded to `runtime.NumCPU()` — each worker holds an open MuPDF document
   through cgo.
3. Per page: `doc.Text(page)` only. No HTML serialisation.
4. Each line is scored by `match.Score`, a five-strategy cascade: case-insensitive
   substring (100), normalised scientific name (95), token equality after normalisation
   (90), Levenshtein ratio via go-edlib (computed), character 3-gram Jaccard similarity
   over short token spans (computed).

   Both computed strategies are **directional**, and that direction is the whole game.
   Strategy 4 slides the *keyword* along a token that is longer than it; sliding a shorter
   token along the keyword asks the reverse question and answers it with 100 for any token
   that is merely a fragment of the keyword.
   A token shorter than the keyword is
   scored by the plain ratio, which charges it for the length it is missing. Strategy 5
   scores *spans* rather than the whole line, because MuPDF extracts some pages as one
   paragraph-long "line", whose n-gram set dilutes any keyword to nothing; spans are sliced
   out of the line by byte offset so the returned word stays a genuine substring of it,
   which the viewer relies on to place the highlight.
5. Lines below `match.MinConfidence` (85) are dropped. That number is now measured rather
   than inherited: `TestThresholdSweep` runs a fixture set of synthetic lines modelled on
   the corpus (no document is quoted) with human verdicts at every threshold from 50 to
   100 and reports the band that classifies them all correctly. It is `[82, 85]`, and 85 is deliberately its top edge — above it the errors
   are missed hits, below it they are near-miss.
   Survivors collapse per
   `(page, foundWord)` into one `SearchResult` whose `Occurrences` counts every hit those
   lines contained, so a term found eight times on one page is eight, not one. Results are
   sorted by confidence descending, then file, page and word — the tie-break exists because
   without it the order came from whichever worker finished first, and the same search
   listed the same files differently twice in a row.
6. Files MuPDF cannot open land in `Outcome.Failures`; files it opens but gets no text out
   of are looked up in the OCR cache, and land in `Outcome.Textless` only if nothing has
   been recognised for them yet. Both are reported in the UI, and the split matters — a
   scanned PDF returns nothing for *every* keyword, so without it "not in this file" and
   "this file cannot be searched at all" look identical to the user. A scan that *has*
   been recognised is searched like any other file; its hits carry `Match: "ocr"` and
   `Outcome.OCRFiles` counts them.
7. The run honours its `context.Context`: a new search cancels the previous one, and the
   cancel button cancels the current one.

Highlights (`frontend/src/composables/usePdfViewer.js`): the backend returns **no**
rectangles. go-fitz exposes no structured text API (only `Text`, `HTML`, `SVG`, `Image`,
`Links`, `ToC`, `Metadata`, `Bound`), so geometry is derived in the frontend: the viewer
locates the term in PDF.js' text layer and composes each text item's own `transform` with
`viewport.transform`. That accounts for glyph metrics, page rotation and a non-zero CropBox
origin. Consequence: a scanned page with no text layer gets no highlight, and the viewer
says so rather than drawing a box in the wrong place.

## How OCR works

Scans have no text layer, so extraction returns nothing for every keyword. `internal/ocr`
gives them one, and `internal/ocr/textcache` makes that a one-time cost.

**When it runs.** Never during a search. Recognition is seconds per page — the 31-page test pdf is minutes — so a search that stopped to OCR
would hang on the first run after a scan is added, with nothing on screen. Instead the
search returns, reports its textless files, and
[OcrPanel.vue](frontend/src/components/OcrPanel.vue) offers to recognise them. The results
the user is already reading stay up while it works, and when it finishes `SearchComponent`
re-runs the same keyword — this time the cache answers, and the scan has hits.

**The offer is a card, not a notice.** It was one more `.notice` strip in a stack of them,
headed by the cause ("enthält keinen durchsuchbaren Text"), and it got read as trivia and
scrolled past. It is the only message in the pane that reports an *incomplete answer* and
also carries the control that completes it, so it is now raised, railed in the warning
colour, and headed by the consequence — "N Dateien wurden nicht durchsucht" — with the
cause and the one-time remedy in plain words underneath. The language dropdown is phrased
as the question it is ("In welcher Sprache sind die Dokumente geschrieben?") so that the
button being disabled until it is answered explains itself; when nothing is selected the
hint under the button says why, and once something is, it says what the run will cost.

**The language is asked for every time.** Tesseract cannot tell German from English by
itself: `--psm 0` detects *script* and orientation, and both are Latin. There is no language
identification in the engine, so something must say which model to load, and a remembered
answer is silently wrong for the next document. The picker lists the installed languages and
adds a combined `deu+eng` when both are present, because Tesseract takes several at once and
lets them compete per word — which is what a German document quoting an English abstract
needs. The choice is cleared whenever the textless file list changes, which is what makes
the question get asked again; it is deliberately *not* in `settings.json`.

**The cache is keyed on content, not path.** `textcache` stores one JSON file per document,
named for the SHA-256 of its bytes. Renaming, moving or re-importing a file reuses its text;
editing it misses and re-runs. The language is recorded *in* the entry rather than folded
into the key — two entries for one document would leave the search with no way to choose
between them, so re-running in another language replaces the entry. Only textless files are
hashed, so the cost falls on the handful of scans rather than on every file in the folder on
every search. Writes go through a temp file and a rename, and a cancelled run caches nothing:
a half-recognised document would otherwise read back as a whole one forever.

**Nothing invites a re-run, so there are two ways out.** A hit is a hit: text recognised in
the wrong language, or by a pipeline since fixed, reads back as an ordinary answer for as
long as the entry survives, and no search will ever notice. `entryVersion` covers the fixes
that ship with a release — it is bumped when the *pipeline* changes and not only when the
stored shape does, and every older entry then reads as a miss (version 2 is the `--psm 1`
change below). Everything else is the user's call: the settings panel reports what the cache
holds and clears it, refusing while a run is in flight, since that run is about to write back
exactly what the user was trying to be rid of. Clearing costs nothing but the recognition
time again.

**Tesseract is a subprocess, not a library.** gosseract would link libtesseract through cgo,
adding a second native dependency to a build that already needs a linker workaround for
MuPDF. One process per page is a rounding error next to the recognition itself.
`ocr.Locate()` prefers a copy bundled at `<exe dir>/tesseract/`, then `PATH`, then the usual
installer paths; `ocr.Status()` reports a missing engine as a state the UI renders, never as
an error. Its wording names the empty path rather than saying "Tesseract ist nicht
installiert": the app ships its own engine, so the real cause is a bundle that never landed
beside the `.exe`, and a user sent off to install Tesseract system-wide fixes nothing. That bundled copy is what the build now ships — see "Bundling Tesseract" below —
so the preference order is not hypothetical: a release always takes the bundled engine, and
whatever is installed on the user's machine cannot silently change which version runs. Pages are rasterised with `doc.ImagePNG(page, 300)` and piped in on stdin, so no
temporary files are involved. Each process runs with `OMP_THREAD_LIMIT=1` and the pool is
one process per core — letting every process fan out again oversubscribes the machine badly
enough to be slower than running them one at a time.

**Every page is read with `--psm 1`, and that is why `osd.traineddata` is bundled.** The
default mode 3 segments the page but never asks which way up it is. A scanned slide deck is
landscape content on portrait paper, so its pages are stored sideways, and mode 3 finds the
text lines but reads them bottom-up: the corpus' first page came back as `younz Bunjpueyeq‑
suolsseideq pun -js6uy Jn wnsjUuez`. Not a poor transcription — a rotated one, matching
nothing, cached forever. Mode 1 is the same segmentation *with* orientation detection, and
reads that page as "Zentrum für Angst- und Depressionsbehandlung Zürich".

Only one of the two rotations is affected: Tesseract's line finder handles a page turned
clockwise unaided, and fails on the counter-clockwise one. So a fixture must be rotated the
failing way to test anything — which is what `Get-Tesseract.ps1` renders. An engine without
`osd.traineddata` warns on stderr, falls back to mode 3 and still exits 0, so nothing in Go
guards for it; the guarantee is the bundle's, and the bundle verifies it by reading a
sideways image back.

**Consequences worth knowing.** An OCR hit cannot be highlighted: the viewer derives geometry
from PDF.js' text layer, and a scan has none. Those hits are marked `OCR` in the result list
and say so in the tooltip. And OCR errors feed the same scorer at the same 85-point
threshold, which was tuned so near-miss drug names fall *below* it — so a wrong-language
model does not just misread, it pushes genuine hits under the gate.

## Building

[build.ps1](build.ps1) is the entry point: it checks the toolchain (go / node / npm / wails
/ gcc, and Wails CLI >= 2.15), runs the Go checks, exports the `CGO_LDFLAGS` workaround
below, calls `wails build -clean` and stages Tesseract beside the binary. `-Dev` runs
`wails dev` instead, `-SkipChecks` skips the checks, `-SkipTesseract` skips the bundle,
`-NoClean` keeps `build/bin`, `-StopRunning` terminates a running app rather than refusing
to build over it, `-Platform` overrides `windows/amd64`. It probes the usual
MSYS2 locations for `gcc` and prepends the one it finds to `PATH` for the build, so MSYS2
does not have to be on the system `PATH`.

**A running app is refused before anything is touched.** `wails build -clean` empties
`build/bin` and then writes the binary. A running instance holds a lock on its own `.exe`,
so the wipe succeeds — taking `build/bin/tesseract` with it — and the write then fails with
`Access is denied`. The script aborts there, which is *before* the Tesseract copy, so what
survives is the *previous* `.exe` with no engine beside it. Launch it and OCR reports the
bundle as missing, with nothing in the chain naming the rebuild as the cause. So
`Assert-NotRunning` checks for the lock up front and fails with that explanation; after
`-StopRunning` kills the process it waits for an exclusive open on the file rather than
trusting the process handle, because the lock outlives the process by a moment and losing
that race lands in the same hole.

Note it is ASCII-only on purpose: Windows PowerShell 5.1 reads a BOM-less file as CP1252,
which turns a UTF-8 em dash into a smart quote and breaks parsing.

Underneath, `wails dev` / `wails build` are the only working entry points on a clean
checkout:

- `go build ./...` → `pattern all:frontend/dist: no matching files found`
- `npm run build` → `Could not resolve "../wailsjs/go/main/App"` (bindings are generated,
  not committed)

Go-only checks that *do* work without the frontend:

```sh
go build ./internal/...
go vet ./internal/...
go test ./internal/match/ ./internal/ocr/textcache/   # no cgo, no C toolchain needed
```

Those two test packages are listed one by one rather than as `./internal/...` on purpose:
`internal/search` and `internal/ocr` import go-fitz, which loads MuPDF at init — through cgo,
or through `libmupdf.dll` on the `nocgo` path — so their test binaries need the toolchain
either way. Keeping the scorer and the cache free of that import is what keeps them testable
on a bare checkout.

Toolchain notes:

- Wails CLI v2.12 cannot generate bindings under Go 1.27 (`internal error: package "os"
  without types was imported`). Use v2.15+.
- go-fitz ships a prebuilt MuPDF static library referencing `__intrinsic_setjmpex`, which
  mingw-w64 v12+ no longer provides. It is MSVC's name for the CRT's `_setjmpex`, which
  mingw does ship in `libmsvcrt.a`, so alias it:
  `CGO_LDFLAGS="-Wl,--defsym=__intrinsic_setjmpex=_setjmpex" wails build`.
  Verified with mingw-w64 GCC 14.1.0 (MSYS2 MINGW64) and go-fitz v1.28.2.

The version in the UI and on the `.exe` both come from `wails.json` → `info.productVersion`;
Vite reads it at build time.

### packaging/ and build/

Wails reads the app icon, the manifest and the version template from `build/`, and writes
its own defaults over anything missing there. It also writes the binary to `build/bin`. That
makes `build/` both a source and an output directory, and there is no way to separate them
from Wails' side — no CLI flag, no `wails.json` key.

So the sources live in [packaging/](packaging/) and are copied into `build/` at the start of
every build; `build/` stays generated and `.gitignore`d in one piece. Edit the icon in
`packaging/`, never in `build/`, where the next build overwrites it.

```
packaging/appicon.png                 source for the generated icons
packaging/windows/icon.ico            the .exe icon
packaging/windows/info.json           version-info template, filled from wails.json
packaging/windows/wails.exe.manifest  DPI awareness, common controls
```

Verified after the move: the `.exe` carries its icon and a fixed file version of `2.0.0.0`
resolved from `wails.json`, and Wails wrote nothing new into `build/` — so it consumed the
copies rather than regenerating defaults. The version *strings* stay empty, which is item 8
in [To-Do.md](To-Do.md) and predates this.

### Bundling Tesseract

[Get-Tesseract.ps1](Get-Tesseract.ps1) stages an engine into `build/tesseract`; `build.ps1`
copies it to `build/bin/tesseract`, which is where `ocr.Locate()` looks first. It is a
packaging step, not a code change — the loader already preferred a bundled copy.

- **Sources, in order:** `-From <dir>`, then an installation already on the machine (the
  same probe list as `Locate()`), then the UB Mannheim installer. Copying an existing
  install costs no download, which is why it comes before the network.
- **The installer is unpacked, not run.** It is an NSIS archive, so 7-Zip reads it without
  executing anything: no system-wide install, no elevation, no uninstaller. `-UseInstaller`
  falls back to `/S /D=` for machines without 7-Zip, and is opt-in precisely because that
  route *does* execute the download.
- **The download identifies itself.** `digi.bib.uni-mannheim.de` answers Windows PowerShell
  5.1's default user agent with 403 — `WindowsPowerShell/5.1` fetching an `.exe` is a
  signature droppers wear — so `Invoke-Download` sends a user agent naming this script.
  Verified: default UA 403, `pdf_scanner-build (+…)` 200.
- **Copy after `wails build`, not before.** `-clean` empties `build/bin`. `-Dev` stages
  first instead, because `wails dev` writes its binary into the same directory and would
  otherwise be the one build where OCR does not work.
- **The prune is 64 MB of the 229 the installer carries**, leaving 175 MB. Almost all of it
  is the other seventeen executables — `lstmtraining`, `text2image`, `mftraining` and the
  rest of the model-building toolchain, ~63 MB — plus ScrollView's `.jar` files and the man
  pages. The app runs exactly one binary, so every other one goes. Language data is pruned
  to what was asked for (`deu`, `eng` by default) and topped up from `tessdata_fast`.
- **`osd.traineddata` is kept, and it is not a language.** `recognize()` asks for
  orientation detection on every page (see `--psm 1` above), so the model is required, not
  optional — 10 MB of the 175. `$models` in the script is `$languages + osd`, and that is
  what gets kept, topped up, listed and verified; `$languages` stays what the picker offers,
  because `listLanguages()` filters `osd` out. Passing `$models` to `Test-Bundle` is also
  what retires a tree staged before this: it now fails the idempotency check and rebuilds.
  The model is byte-identical in `tessdata`, `tessdata_fast` and `tessdata_best`, so
  `-TessdataRepo` needs no special case for it.
- **The DLLs are deliberately left whole.** What remains is dominated by
  `libtesseract-5.dll` (97 MB) and ICU's data table (29 MB), both load-bearing. The ones
  only the training tools wanted — pango, cairo, fontconfig — are about 10 MB against 175,
  and guessing wrong there yields an app that will not start on a user's machine.
- **The staged tree is verified by running it**, twice over: every model has to come back
  from `--list-langs` under the same `TESSDATA_PREFIX` the app sets, and a rendered fixture
  has to come back recognised. The second check is what guards the prune —
  `--list-langs` answers happily from a tree whose engine no longer works, and it will name
  an `osd.traineddata` the engine cannot load.
  The fixture is four lines of German rotated *counter-clockwise* and read with `--psm 1`,
  which is the only shape that fails when `osd` is broken: an upright fixture reads back
  either way, and so does a clockwise one. Four lines rather than one word because
  orientation detection answers a single word with "Too few characters. Skipping this page".
  It writes a temp PNG rather than piping one in as the app does, because
  PowerShell cannot reproduce the app's invocation: `$proc.StandardInput` is a StreamWriter
  whose UTF-8 preamble reaches the pipe first, Tesseract then sees no PNG signature and
  falls back to reading stdin as a list of filenames. Go's `bytes.NewReader` has no
  preamble. Nothing pruning can break is lost by the substitution.
- **Native tools are called through `Invoke-Tool`.** Windows PowerShell wraps every stderr
  line from a native command in an ErrorRecord, and under `$ErrorActionPreference = 'Stop'`
  a plain `& $exe … 2>&1` therefore aborts the script over output it was collecting on
  purpose. Tesseract prints diagnostics on runs that succeed. The exit code is the verdict;
  stderr is evidence.
- **A failed bundle warns, it does not fail the build.** The app treats an absent engine as
  a state it renders, so a build without one is a working build that cannot read scans.
  Failing here would block a release over a machine being offline.

The installer version is pinned in the script's `-Version` default. The mirror keeps only a
handful of builds and drops old ones, so a 404 there means picking a newer one from
`https://digi.bib.uni-mannheim.de/tesseract/` — checked 2026-08-22, the newest it carries is
`5.4.0.20240606`.
